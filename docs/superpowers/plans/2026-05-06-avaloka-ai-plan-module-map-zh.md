# Avaloka AI 计划步骤与系统模块对应表

日期：2026-05-13

状态：中文主文档

## 1. 这份文档解决什么问题

这份文档把 Avaloka AI 的计划步骤对应到系统图里的模块，帮助你看清楚：

- 每一步到底在建设哪个模块。
- 为什么这个步骤重要。
- 哪些步骤属于当前 7 天验证。
- 哪些步骤属于后续完整 MVP。

## 2. 系统模块编号

| 编号 | 模块 | 目的 |
|---|---|---|
| M0 | 同意与边界说明 | 告诉用户 Avaloka 能做什么、不能做什么，防止被误解为治疗或危机服务 |
| M1 | 聊天界面 | 给用户一个私密、简单、低压力的倾诉入口 |
| M2 | 危机安全闸门 | 识别自伤、自杀、伤害他人和急性危机场景 |
| M3 | 支持需求判断 | 判断用户此刻需要稳定、倾听、澄清、陪伴还是现实求助，避免诊断化 |
| M4 | 场景回应库与智慧检索 | 第一阶段用 20 条高质量回应库，后续再接小型 RAG |
| M5 | 慈悲智慧回应链 | 生成温暖、清明、实际的回应 |
| M6 | 输出质量检查 | 防止回答空泛、说教、过长或不安全 |
| M7 | 五项正念守护 | 确保输出不破坏尊重生命、真爱、爱语、滋养等底线 |
| M8 | 使用与反馈记录 | 记录真实低谷使用、评分、继续使用意愿和失败原因 |
| M9 | 本地对话记忆 | 保留必要上下文，让陪伴有连续性 |
| M10 | Markdown 智慧知识库 | 存放场景、回应样例、安全规则、语言风格 |
| M11 | 知识导入管线 | 把 Markdown 切分、清洗、写入向量库 |
| M12 | 向量数据库 | 存储并检索相关知识片段 |
| M13 | 本地模型 | 在本地生成回应，降低隐私风险 |

## 3. 当前最高优先级：7 天免费用户验证

| 步骤 | 对应模块 | 目的 |
|---|---|---|
| 写一页用户实验说明 | 产品/商业验证，不属于单一技术模块 | 让测试目标、用户、流程、成功标准清楚 |
| 招 5 位目标用户 | 产品/商业验证 | 验证真实用户是否存在，而不是只验证想法 |
| 做一个极简聊天 MVP | M0, M1, M5 | 让用户理解边界、能真实倾诉，并得到基础回应 |
| 加 crisis safety gate | M2 | 防止危机场景被普通陪伴流程处理 |
| 加 Five Mindfulness Guardian | M7 | 确保每条回应背后符合伦理与安全底线 |
| 准备 20 条高质量场景回应 | M4, M5, M6, M7 | 保证测试时的回应质量足够高，并能通过守护 |
| 跑 7 天测试 | M0-M8 | 观察用户真实低谷时是否会打开并连续使用 |
| 第 7 天确认是否想继续免费使用 | M8 + 商业验证 | 先验证继续使用意愿，不做付费测试 |
| 根据真实记录改商业书 | M8 + 产品/商业验证 | 用用户行为而不是想象改商业计划 |

## 4. 为什么这个优先级正确

现在最大的风险不是技术做不出来，而是：

- 用户是否真的会在痛苦时打开它。
- 回应是否真的让她觉得被接住。
- 她是否愿意连续 7 天使用。
- 免费测试后她是否主动想继续用。
- 安全边界是否足够清楚。

所以第一阶段应该先验证用户行为，而不是先做完整系统。

## 5. 后续完整 MVP 的技术任务映射

| 技术任务 | 对应模块 | 说明 |
|---|---|---|
| 建立项目骨架 | 全局 | 为后续模块提供代码结构 |
| 建同意与边界说明 | M0 | 首次使用前说明非治疗、非医疗、非危机服务 |
| 建聊天 UI | M1 | Streamlit 或简单网页界面即可 |
| 实现危机检测 | M2 | 用规则和测试用例先覆盖最危险场景 |
| 实现支持需求判断 | M3 | 将用户输入整理成场景、主题、需要，避免诊断化 |
| 建 20 条场景回应库 | M4 | 第一阶段优先于 RAG |
| 实现回应链 | M5 | 按“听见-照见-转念-行持”生成 |
| 加输出质量检查 | M6 | 检查语言、长度、安全、实用性 |
| 加五项正念守护 | M7 | 每条非危机回应必须通过 |
| 加使用与反馈记录 | M8 | 支持 7 天验证和商业书更新 |
| 加本地记忆 | M9 | 保留必要上下文，不做过度记录 |
| 建立知识库 | M10 | 先小而精，不做大规模内容 |
| 做知识导入 | M11 | 将 Markdown 文档切分成可检索片段 |
| 接向量数据库 | M12 | 支持语义检索 |
| 接本地模型 | M13 | 使用本地 LLM 生成回应 |

## 6. 当前不要优先做的事

这些事情可以以后做，但不应该在 7 天验证前抢优先级：

- 复杂账号系统。
- 付费系统。
- 大规模内容库。
- 社群。
- 语音、音乐、仪式感体验。
- 多模型调度。
- 精美 UI。
- 大规模自动化评估平台。

原因很简单：这些都不能替代真实用户连续使用的证据。

## 7. 一句话总结

Avaloka 的计划应该先证明“5 位目标用户会不会在真实低谷时连续使用一个很粗糙但有慈悲智慧的工具”，再决定是否扩大工程范围。
